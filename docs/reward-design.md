# 奖励设计原则

这一页是这个项目**最贵**的知识：它来自七轮"训出来一看不对、回头量、再改"的循环
（具体过程在 [失败模式史](failure-modes.md)）。原则本身可以搬去别的任务。

::: info 上游 `microduck_rl` 的 AGENTS.md 原话（本项目多处引用的源头）

*ANY positive reward for BEING in a fallen-ish state gets farmed — the policy parks in
the cheapest qualifying pose and farms it.*
*a 25 cm robot tumbles at 3.5–5.5 rad/s NATURALLY — don't impose human-scale speed
intuitions via caps; put anti-violence pressure on impacts and thrash, not on rotation speed.*
*motion-blockers must stay LOW.*

:::

## 一、看"奖励质量"，不看"权重"

权重是设计意图，**质量是实际发生的事**。两者经常不一致：

| 项 | 权重 | 实测贡献（vx=0.15） | 结论 |
|---|---|---|---|
| `air_time` | 3.0 | **+2.51/步** | 真正的现金牛 |
| `upright` | 2.0 | +1.97/步 | 有效 |
| `track_lin_vel` | 2.0 | +1.90/步 | 有效 |
| `track_ang_vel` | 1.0 | +0.51/步 | 只拿到一半 —— 偏航是"放弃掉的那一半" |
| `head_dev` | -0.2 | **-0.04/步** | 太弱，等于没管（见 [行走任务](tasks/walk.md)） |
| `body_ang_vel` | -0.01 | **-0.00/步** | 死项 |
| `angular_momentum` | -0.01 | **≈ -1e-7/步** | **完全没接上**（量纲问题，见原则七） |

**做法**：改奖励前后各跑一次 `uv run python scripts/eval_walk.py <ckpt> --terms`。
不跑这一步就改权重，等于闭着眼睛调参。

## 二、绝不给"处在坏状态"发正奖励

反面模式：任何**无条件**的正奖励（`air_time`、`upright`、`track_lin_vel`…）
在"躺平 / 趴着 / 头撑地"这些姿势下**依然可拿**，策略就会去那里扎堆 ——
因为没有比"躺着还能拿分"更省力的事。

**解法是软门（gate），不是删项**：

- `_posture_gate` = 躯干高度斜坡 × 直立程度斜坡，**乘在** `track_lin_vel` / `track_ang_vel` / `air_time` 上。
  躺平（0.041 m / 50°）→ 门 = 0；站立 → 1。**是软斜坡，不是 if**：爬起来有递增的分，梯度一直在。
- `_progress_gate` = "指令方向上的速度 / 指令大小"，**乘在** `air_time` 上。
  原地蹦、横着挪、反向走都拿不到步态奖励。
- 三道防线缺一不可：**姿态门**（不在坏姿势）+ **方向门**（不是在乱动）+ **倒地终止带宽限**
  （`fallen_too_long`：倒地 1 秒才终止，留恢复样本，但躺着不能永久薅分）。

::: tip 写门的时候要问自己两个问题

1. **坏状态确实被压到 0 吗？**（`test_gait_rewards_are_gated_by_posture`：躺平 <1e-6）
2. **好状态没有被误伤吗？**（`test_stance_penalty_is_calibrated_on_measured_stance`：
   自然站姿 cost <0.01，叠上正常迈步的膝屈增量 <0.3）

:::

## 三、势能型 Δ 项不可薅

"提升"比"保持"值得奖励时，用**势能差**（Δ），不要用"当前状态"：

- `upright_progress` = Δcos(倾角)：**爬起来付钱、保持付零**，躺着不付钱，因此无法farm。
- `height_progress` = Δz：同理。

⚠️ 注意本仓库现在的 `upright` 是**状态型**（高斯核，权重 2.0）——
它能工作是因为**同时**有姿态门把躺平时的其他奖励清零。换任务时要重新想清楚：
状态型奖励必须配一个"坏状态没分"的结构，否则就会被薅。

## 四、motion-blocker 的权重必须低

`body_ang_vel`、`action_rate`、`joint_vel` 这类"罚动作本身"的项，
罚的是**走路必然要产生的量**。权重一大会让策略选择"不动"：

- 实测：`action_rate` 权重 -0.30 时每步 **-1.66~-3.0**，占全部罚项 **85%**，
  而且正好压在"鸭子尝试迈步"的训练窗口上 ⇒ **有脚离地从 32% 掉到 0.9%**（策略学会别动）。
- 正确的量级是"平时占正质量的百分之几"：现在 `action_rate` 终值 -0.10 ≈ 3~9%，
  `body_ang_vel` 正常走路只占正质量 **0.2%**、踉跄时才涨到几个百分点 ——
  **平时不干扰、出事才咬**，这才是 motion-blocker 该有的样子。

::: danger 别用'加了正则所以更稳'说服自己

`angular_momentum` 权重 -0.01 看着像个稳定项，实测量级只有 **1e-7 = 等于没接**
（鸭子太小，`|L| ∝ 质量×尺度²` 只有 0.003~0.008，平方后乘 -0.01 就没了）。
加任何一项之前，**先量它到底有多大**。

:::

## 五、`std` 要按自己的指令尺度定，不能跨任务照抄

跟踪核 `exp(-(err/std)²)` 里的 `std` ≈ **"你还在乎的误差"**。
上游的 `std=0.316` 是配他们 ±0.4 m/s 指令尺度的；我们的指令尺度小 4 倍，
照抄同一个 `std` 的后果实测是：**站着不动白拿 90% 的跟踪分，好步态只多 0.06 分/步** ——
于是 500 轮训出来的策略就是"站着不动"（[失败模式](failure-modes.md)）。

现在的值 `std=0.20` 是**用"真步态"标定**出来的：上游 `alpha_walking.onnx`
在同环境里只做到指令速度的 ~45%，所以 `std` 必须宽到"45% 精度仍然拿得到分"，
否则会惩罚一切真实步态。标定脚本：`scripts/eval_upstream_policy.py`。

## 六、课程的每一档都要跟"策略已经学会什么"对齐

课程不是"时间表"，是"**在策略当前能力边缘施压**"。两个反例：

- `air_time` 窗口下限一上来就是 0.125 s：而实测鸭子**一开始只能摆动 20~30 ms** ⇒
  "抬脚 30 ms"和"完全不抬"同分 ⇒ **迈步这件事零梯度，永远学不会第一次抬脚**。
  现在的做法：从 **0.03** 起步，6000 步后 0.08，12000 步后 0.125。
- 课程最后一档排在 14000 步 ≈ 580 轮：而推荐的验证跑是 500 轮 ⇒ **那一档永远不生效**。
  所以测试里有一条"两套课程最后一档 ≤14000 步"的硬约束（`test_regularizer_weights_...`）。

还有一个跨任务的坑：课程按 `env.common_step_counter` 推进，而**它每次 `env.step()` 只 +1**
（所有环境一起走）⇒ **课程推进速度只跟 iteration 数有关、跟 `num_envs` 无关**。
`num_steps_per_env=24` 时，无论 16 还是 4096 个环境，1 个 iteration 都只让课程前进 24 步。

## 七、加任何正则之前，先量它的量级和符号

两件事都要做：

1. **量级**：`scripts/walk_p0_probe.py` 的 ⑦ 段就是干这个的（零动作 vs 随机乱蹬两种状态下的中位数）。
2. **符号**：负权重项的返回值必须 ≥0，否则"违规即奖励"。
   测试 `test_penalty_signs_are_negative_costs` 遍历所有负权重项检查这一点
   （上游管这叫 *infallible check*）。

## 八、地面真值探针必须代表**整片接触区域**

"脚抬多高"这种量，最容易被一个"看起来对"的单点探针骗过去。实测三种错法：

| 探针 | 脚底贴地、脚踝从 −30° 转到 +30° 时的漂移 |
|---|---|
| 脚踝 body 的位置 | +10.9 mm |
| 脚底 site 的位置 | **+14.1 mm（更差）** |
| 上游那套射线传感器 | 平地上退化成 site 高度（ring 偏移在水平面内） |
| **脚底网格采样点取 min（53 点/脚）** | **≤1.93 mm** ✅ |

教训：**先证明探针在"真值已知的极端姿态"下不漂，再用它做奖励。**

## 九、改奖励的固定流程（零成本重打分）

改奖励**之前**先做这一步，能省掉一整轮 GPU：

```bash
# 1. 拿旧 checkpoint, 在**新奖励**下重新打分: 行为排序翻转了吗?
uv run python scripts/eval_walk.py <old>/model_250.pt <old>/model_499.pt --terms

# 2. 量级对不对(负项占正质量多少)、符号对不对
uv run python scripts/walk_p0_probe.py --envs 4 --steps 200

# 3. 达标才谈训练; 训练后立刻用同一套脚本复测行为
uv run python scripts/eval_walk.py <new>/model_XXXX.pt --terms
```

第 1 步的真实例子：当年"新奖励"下**走路 +2.88 / 站着 +2.82 仍然是平局** ——
拆项发现 `body_ang_vel` 一项就占走路罚项的 **-0.426**；把它降到 -0.01 之后排序才翻转
（+3.17 vs +2.98）。**如果当时直接上 GPU，会白跑一整轮。**

## 检查清单

改任何奖励/课程项之前，逐条对照：

- [ ] 这一项在**坏状态**下会不会白送分？（需要门吗？软门还是终止？）
- [ ] 这一项在**好状态**下会不会误伤？（用实测姿势/步态标定，不要用 XML 默认）
- [ ] 权重对应的**实测质量**是多少？（`--terms`）/ 占正质量多少%？
- [ ] 它是状态型还是 Δ 型？状态型要配"坏状态没分"的结构。
- [ ] 它是不是 motion-blocker？（是的话，量级要"平时 0.2%、出事才咬"）
- [ ] 课程档位跟"策略现在的水平"对齐吗？最后一档在验证预算内吗？
- [ ] 符号对不对？（负权重项返回值必须 ≥0）
- [ ] 有没有一个**测试**能防止它被改回去？
