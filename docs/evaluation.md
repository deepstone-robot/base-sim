# 评估与探针

## 为什么不能只看训练曲线

TensorBoard 上的 `Episode_Reward/*` 有两个会骗人的性质：

1. **它是"每秒平均贡献"**：`Episode_Reward/<项> = 该项整回合累计 / max_episode_length_s(20s)`。
   一个回合如果在 2 秒就终止了，它的数值会被压小十倍 —— 于是"早早摔倒"的策略在某些项上看不出异常。
2. **它把行为压成一个数**。`air_time` 掉了 0.3，可能是"不抬脚了"，也可能是"抬得更高更久但方向不对"；
   曲线区分不出来。

所以本项目的规矩是：**要改动奖励/课程/模型之前，先用 headless 脚本量一次行为**。
这一页就是那套工具。三层递进，成本从秒到十几分钟：

| 层 | 工具 | 时间 | 回答什么 |
|---|---|---|---|
| 1 | `pytest tests/` | 秒级 | 我有没有写坏维度/资产名/课程边界（[测试](testing.md)） |
| 2 | `scripts/eval_walk.py` | 分钟级 | 这个 checkpoint 到底会不会走：跟踪误差、步态、终止原因 |
| 3 | `scripts/probe_*.py` | 几分钟~十几分钟 | 为什么会这样：摆动相位、摇头机理、随机化到底生不生效 |

::: info 这一页里"实测"与"声称"的区别

标 **实测** 的数字是本次会话真跑出来的（命令在页面上，可复现）；
标 **docstring 声称** 的是写在脚本注释里、我没复跑的历史记录。
两者都有价值，但引用时不要混。

:::

## 脚本依赖关系

```
view_microduck.py                    独立：交互式看图（必须 mjpython）
eval_walk.py                         评估基座：build_env / load_policy / _FEET_CONTACT_SENSOR
 ├── probe_gait_wobble.py            量"摇头晃脑"（还借 eval_upstream_policy 的 build_obs/onnx_actions）
 ├── probe_head_wobble.py            量"摇头"（还借 probe_gait_wobble 的 dominant_freq/quat_to_yaw）
eval_upstream_policy.py              在自己的环境里跑上游 ONNX（教师/对照组）
probe_sim2real_dr.py                 逐项验证随机化是否真生效（独立入口，无参数）
walk_p0_probe.py                     九段数字台账（前 6 段不建环境）
```

因为 `probe_*` 都建在 `eval_walk.build_env` 上，**它们和正式评估用的是同一个环境构造路径** ——
这是故意的：探针里看到的数字，必须和评估时的行为同源。

## `eval_walk.py` —— 评估基座

```bash
# 单次：看一个 checkpoint
uv run python scripts/eval_walk.py logs/rsl_rl/microduck-walk/<run>/model_3250.pt
# 对比多个轮次（同一张表里逐行）
uv run python scripts/eval_walk.py <run>/model_0.pt <run>/model_250.pt <run>/model_499.pt
# 逐项奖励：给旧策略在**新奖励**下重新打分（零训练成本的核心手法）
uv run python scripts/eval_walk.py <run>/model_499.pt --terms
```

| 参数 | 默认 | 作用 |
|---|---|---|
| `checkpoints` | — | 一个或多个 `model_*.pt` |
| `--num-envs` | 64 | 评估并行环境数 |
| `--steps` | 400 | **每个指令配置**跑多少步 |
| `--max-configs` | 5 | 只跑指令网格前 N 个（快速横向对比） |
| `--vx` | 无 | 只测这一个前进速度，跳过整个网格 |
| `--track-std` | 无 | 临时覆盖跟踪核 `std`（标定用） |
| `--terms` | 关 | 额外打印逐项奖励（每步真实量级） |

它跑的是**受控指令**：关掉随机推、关掉课程、固定 vx/wz，指令网格是
`[(0,0), (0.15,0), (0.30,0), (0.15,+0.3), (0.15,-0.3)]`
（刻意留 `vx=0` 是为了看"能不能原地站住"）。

### 主表怎么读

| 列 | 含义 |
|---|---|
| `指令(vx,wz)` | 本行用的固定指令 |
| `vx实体` / `vy实体` | 实际**机体系**速度的**有符号**均值；`vx` 该接近指令、`vy` 该接近 0（非零 = 横着走） |
| `vx误差` | `\|实测机体系 vx − 指令\|` 的均值；**站着不动时 ≈ \|指令\|** |
| `\|vz\|` | 竖直速度绝对值均值（"上下乱窜"） |
| `倾角` | 由 `projected_gravity_b` 反算的倾斜角（度） |
| `躯干z` | 躯干世界高度 |
| `姿态门` | `_posture_gate` 均值：1 = 站/走，0 = 躺/趴。**< 0.5 说明它在爬/躺**（那种姿势下技能类奖励被乘成 0） |
| `离地%` | 有脚离地的步数占比 |
| `摆动s` | 每次摆动（离地→落地）的平均时长 |
| `峰值mm` | 每次摆动中**脚底最低点的峰值高度**（这才是"抬脚抬多高"） |
| `步/回合` | 平均活了多少步（50 Hz）；旁边是终止原因计数 |

### 两个必须知道的口径陷阱

::: danger `episode_length_s` 必须在构造环境之前设

回合长度会烘进 termination manager。**构造完再改 `env.episode_length_s` 不生效** ——
症状是"正好在第 200 步全体终止"（4 s × 50 Hz），看起来像策略集体摔了，其实是配置没吃上。
`build_env(..., episode_length_s=...)` 就是为此加的入口。

:::

::: warning `_step_reward` 与 RL 拿到的不一样

`env.reward_manager._step_reward` 是**未乘 `dt`** 的每步加权值；RL 真正优化的是它 ×`step_dt`。
评估脚本打印的是前者（"每步真实量级"），因为这样和"某项值不值得"的直觉一致。
对比训练曲线时别把这个数乘上 dt 再乘一遍。

:::

### `--terms` 的输出（实测，`model_3250.pt`，vx=0.15）

```
逐项: 合计 +6.528 | 正 +6.893 | 负 -0.365
  air_time=+2.51  upright=+1.97  track_lin_vel=+1.90  track_ang_vel=+0.51
  stance_dev=-0.16  joint_vel=-0.10  head_dev=-0.04  joint_pos_limits=-0.04
  action_rate=-0.02  foot_clearance=-0.00  body_ang_vel=-0.00  foot_slip=-0.00
```

**这张表是奖励设计的唯一依据**：它立刻回答了"某个权重是不是摆设"。
例如 `body_ang_vel` 权重是 -0.01、实测贡献 -0.00 —— 它根本没在起作用；
`head_dev` 权重 -0.2、实测 -0.04，而 `air_time` 一项就是 +2.51。

## `probe_gait_wobble.py` —— 量"摇头晃脑"（躯干）

```bash
uv run python scripts/probe_gait_wobble.py model_3250.pt --vx 0.15 --steps 400
```

一次前向 rollout 提时间序列，不提训练。输出六块：摆动幅度表、姿态角（含**去趋势**分解）、
摆动频率表、原始序列自检、**路径几何**、以及"扭动 vs 左右脚载荷"的互相关。

| 判决线索 | 含义 |
|---|---|
| `主频 / 步频 ≈ 1.0` | 摆动就是左右重心转移，**正常步态，不用管** |
| `≈ 0.5` | 每两步晃一次 → 极限环，该用奖励压 |
| 远离整数 | 躯干共振 / 控制带宽不够 → 查 `action_rate` / `body_ang_vel` |
| 侧向速度 / 前进速度 < 25% | 算走得干净 |
| **互相关 \|r\| > 0.5 且滞后稳定** | 扭动**先于**抬脚 ⇒ 是倒重心的**机制**，别硬压 |
| \|r\| < 0.3 或滞后每局乱 | 只是抖动，可以用奖励压掉 |
| `路径直线度(净位移/路程)` | 1.0 = 笔直；0.5 以下 = 明显绕圈 |

**实测结论（`model_3250.pt`，8 环境 × 400 步）**：

| 指标 | vx=0.15 | vx=0.30 |
|---|---|---|
| 实际速度 | 0.166 m/s | 0.302 m/s |
| 倾角 | 1.44° | 1.86° |
| 躯干偏航摆动（去趋势） | ±12.4° | ±12.4° |
| 偏航角速度 RMS | 1.86 rad/s（峰值 ≈240°/s） | 1.67 rad/s |
| 摆动主频 / 落脚步频 | 1.625 / 1.750 Hz | 1.750 / 1.875 Hz |
| 侧向速度 / 前进速度 | 21% | 12.6% |
| **路径直线度** | **0.954** | **0.974** |
| 扭动 vs 脚载荷 互相关 | **滞后 −4.5 步，\|r\|=0.59（8/8 一致）** | 滞后 −3.0 步，\|r\|=0.67 |

判决：**摆动锁在步频上、且领先抬脚 60~100 ms ⇒ 那是这只机器人的倒重心机制，不是缺陷。**
（自检也成立：由 `|wz|` RMS 反推的偏航角峰峰值 29.5° vs 实测残差 27.3°，比值 1.08。）

## `probe_head_wobble.py` —— 量"摇头"（头/脖子链）

```bash
uv run python scripts/probe_head_wobble.py model_3250.pt --vx 0.15 --steps 500
uv run python scripts/probe_head_wobble.py model_3250.pt --steps 200 --freeze-head   # A/B
```

| 输出块 | 回答什么 |
|---|---|
| ① 头关节偏离/主频/与 wz 相关 | 四个头关节各自偏离默认姿势多远、以什么频率动 |
| ② 嘴尖在**躯干坐标系**里摆动 | 眼睛里看到的"摇头"幅度（躯干系里量，天然剔除了躯干自身的转动） |
| ③ 头链质心 + 折算到整机质心 | 点头/摇头到底有没有在搬质心 |
| ④ 头摆动 vs 左右脚载荷 互相关 | 与躯干扭动同一把尺子：有稳定滞后 = 有功能 |
| ⑤ 动作 RMS vs 实际偏离 | **是策略主动甩，还是软伺服被甩起来的** |

**实测结论（`model_3250.pt`，vx=0.15，8 环境 × 500 步）**：

- 头关节偏离默认姿势：`neck_pitch` 26.6°、`head_pitch` 25.0°、**`head_yaw` 37.2°（峰值 57.2°）**、
  `head_roll` 9.8°，**全部锁在步频 1.700 Hz**。
- 嘴尖（躯干系）左右摆动 **RMS 33.9 mm / 峰峰 94 mm**。
- 与左右脚载荷互相关 **|r| = 0.92，8/8 环境一模一样**。
- 但头链质心只动 **7.0 mm** ⇒ 折算整机质心 **2.7 mm = 两脚间距的 4%** ⇒ **太小，当不了配重**。
- ⑤ 显示动作目标本身在扫（`head_yaw` 目标 RMS 45.4°），而实际只到 37.2°；
  `neck_pitch` 目标 12.4° 而实际偏离 26.6°（比值 2.2）⇒ **位置伺服追不上这个重的头**。

**零成本 A/B（`--freeze-head`，把 4 个头通道置零）实测**：

| | 倾角 | 侧向速度/前进 | 路径直线度 | 头链质心横向 | 头/脚载荷 \|r\| |
|---|---|---|---|---|---|
| 正常 | 1.5° | 21% | 0.95 | 7.04 mm | 0.92（8/8 一致） |
| 冻头 | **4.6°** | **59.5%** | **0.66** | **0.04 mm** | 0.58（0.31~0.90 乱） |

三条推论：

1. **现有策略是靠甩头稳住自己的** —— 直接冻结会让步态明显变差（这是"训练时带头自由度的策略依赖头"，
   不等于"从头冻掉重训一定更差"）。
2. 头链质心的横向运动**几乎全是被"命令"出来的**（7.04 mm → 0.04 mm），不是被动甩的；
   起作用的是它的**角动量**（反作用轮），不是位置。
3. 冻结后 `neck_pitch` 仍有 **7.2° 的残余下垂** = 位置伺服托不住这个重的头（重力下垂）。

## `eval_upstream_policy.py` —— 拿上游策略当教师/对照

```bash
uv run python scripts/eval_upstream_policy.py alpha_walking.onnx --vx 0.15 --terms
```

**为什么值钱**：`../microduck/policies/alpha_walking.onnx` 是上游训练好、真机在用的走路策略，
接口与我们的环境完全兼容（读 ONNX metadata 核对过：61 维 obs =
`base_ang_vel(3) + projected_gravity(3) + joint_pos(14) + joint_vel(14) + actions(14) + twist(3)
+ head_pose(4) + body_pose(6)`，`action_scale=1.0`，站姿与关节顺序一致，归一化已烘进图）。
所以它能当**"这个环境能不能承载一个真走路策略"的判据**，也能用来给我们的奖励做**标定**。

**实测**（docstring 声称 + 本会话复核过输出格式）：

- 它**能走**：离地 46%、摆动 170 ms、倾角 2.8°、零摔倒。
- 但它只跑到指令速度的 **~45%** —— 而且**在他们自己的环境里也是 36~50%**，
  说明那是**他们策略的精度**，不是我们环境的问题（这条 A/B 是当时最重要的一个判断）。
- 用它做标定抓出两处错误：`air_time` 上的"跟踪核"把速度误差平方级罚了两次（真步态输给站着不动），
  以及 `std=0.10` 比真步态的实际精度还严。修完（去掉跟踪核因子 + `std 0.10 → 0.20`）后
  **走 > 站 > 溜** 在每个指令下都成立。

```bash
# 也能换成上游的仿真设置做 A/B（timestep 0.005 × decimation 4 = 同样 50Hz 控制）
uv run python scripts/eval_upstream_policy.py alpha_walking.onnx --upstream-sim
```

`_POLICY_DIR` 是**硬编码的本机绝对路径**（`/Users/junbo.dai/projects/microduck/policies`），
换机器要么传绝对路径、要么先改这个常量。

:::

## `walk_p0_probe.py` —— 九段数字台账

```bash
uv run python scripts/walk_p0_probe.py            # 默认 4 envs × 200 步（CPU 秒级，首次编译 warp 内核 1~2 分钟）
```

这个脚本的作用不是"评估策略"，而是**把每条设计决策背后的数字留下来**。九段对应九条结论：

| 段 | 量化了什么 | 结论（实测） |
|---|---|---|
| ① 探针几何 | 脚底贴地时转脚踝，四版"离地高度"探针各漂多少 | 脚踝 body +10.9 mm、脚底 site +14.1 mm（更差）、上游射线在平地上退化成 site 高度；**采样点取 min ≤1.93 mm** |
| ② 动作尺度 | 抬脚需要的膝屈，在 `scale=0.5/1.0` 下策略要输出多大 | 0.5 时抬脚要 1.0~1.8σ（命中率个位数~20%），1.0 时 <1σ ⇒ 学习信号从一开始就稠密 |
| ②b 站着不动的捷径 | 逐档算"站着不动能白拿多少跟踪奖励" | 旧配置第 1 档 `std=0.25` 下站着白拿 90%，好步态只多 0.06 分/步 ⇒ **策略理性选择是站住**；改成 `std=0.10` + 下限抬到 0.10 后学习信号放大到 ~1.5 分/步 |
| ②c 姿态门标定 | 五种实测姿势下"还靠腿站着吗"的门值 | 躺平（0.041 m / 50°）门 = 0；站姿门 = 1 |
| ②d 方向进度门 + 站姿基准 | 原地蹦该拿 0；姿态罚的基准必须用实测站姿 | 站立时踝关节比 XML 默认转 **17.6°** ⇒ 拿 XML 默认当基准等于按"它站不到的姿势"扣分 |
| ③ upright | 不同倾角下线性版 vs 高斯版每步得分 | 高斯版在 10° 处比线性版硬 ~140 倍 |
| ④ 步态奖励质量 | 一个步态周期内 `air_time` 旧写法（落脚一次性）vs 新写法（每步付） | 旧写法 0.5 分/周期 ≈ 0.014 分/步，相对速度跟踪**等于不存在** |
| ⑤ action_rate 阶梯 | 按"正质量份额"对齐而不是照抄数字 | 旧权重 -0.30 实测每步 -1.66~-3.0、**占全部罚项 85%**，正好压在"尝试迈步"的窗口上 ⇒ 有脚离地从 32% 掉到 0.9% |
| ⑥ 环境内健全性 | 接触相里脚底最低点是否读出 ~0 | 读数在 ±0.5 mm 内晃（接触求解器柔度） |
| ⑦ 动态正则量级 | `body_ang_vel` / `angular_momentum` 两项到底多大 | 前者正常走路占正质量 0.2%、出事才咬；后者只有 **1e-7 量级 = 等于没接** |
| ⑧ 观测契约 | actor/critic 维度与槽位语义 | walk 与 stand 的 actor 都是 51 维但**尾部语义不同** ⇒ 续训会静默错训 |
| ⑨ 奖励体检 | 逐项打印加权后的量级与符号 | 唯一硬判决：**负权重项加权后必须 ≤ 0**（符号反了就是"违规即奖励"） |

## 已知问题（用之前先知道）

| 位置 | 问题 |
|---|---|
| `probe_sim2real_dr.py` 的 `spread` 算式 | `float(f.max(...).min() and (...))` 用 `and` 短路当守卫，**碰巧能跑**；前项恰为 0 时结果会变成 0 |
| `eval_walk.py` 的落脚分支 | 有一小段死代码（`if air[b,f] >= 0: pass`），实际靠 `last_air_time` 取值 |
| `walk_p0_probe.py` 的段号 | docstring 里的段序与 `main()` 实际打印顺序不完全一致（⑥ 排在 ②c/②d 之前），读表时别对错号 |
| `eval_walk.py` / `probe_*.py` | 都用了 mjlab 私有属性（`reward_manager._step_reward`、`sim.mj_model`），升 mjlab 版本时要重跑 |
| `eval_upstream_policy.py` / `probe_gait_wobble.py` | 上游 ONNX 目录是硬编码绝对路径 |
